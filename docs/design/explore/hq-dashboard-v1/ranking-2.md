# Ranking — juror 2

- ranked: variant-a > variant-c > variant-b

## Why variant-a over variant-c

1. A keeps the brief's three "always visible" surfaces (KPI row, event timeline, approval inbox) as distinct panels, and the inbox table shows verdict, ₹ amount and kill-criteria state for all seven pending rows at once (Kaveri Foods "Clear", Trellis Logistics "1 breached", NeoKirana "Breach: burn cap", Vistara Mobility "Breach: runway"). A user can scan every open decision's three required facts in one pass. C compresses the same idea into a single inline tag per row ("burn ok"), which states only one criterion and leaves runway/margin unstated on the row itself — less complete against "kill-criteria state ... visible before the action, never behind a click."
2. A's destructive and error language is exact and specific: the kill button reads "Kill Vistara Mobility — halts funding — unrecoverable," and the failed row reads "Failed: kill NeoKirana — spine write conflict. Next: retry, or escalate to Karthik Subramaniam (L3)" — venture named, consequence named, next step named, matching the brief's error/destructive-language rules almost verbatim. C's kill button is equally strong, but its own failed-capture row ("Capture failed — payment gateway timed out. Retry the capture, or mark it settled manually") never escalates to a named person the way A does elsewhere on the same screen.
3. Both declare a five-state matrix, but A's reference block is legible against the brief's own five words (loading/empty/disabled shown as reference, error/success shown live in the inbox and done log) — a reader can check each word off directly. C relabels the error state as "unresolved" throughout, and nowhere on the page is a reject-reason prompt actually shown (A at least prints "reject — reason required" as a persistent header rule, even without opening the prompt).
4. C's single genuine advantage: its resume banner ("Position in the day: event 3 of 10 ... Resuming at the earliest unresolved event ... events after now are not yet disclosed") is the clearest single passage in the run answering "what does the user see on return after interruption." But that strength costs C a plain first read — the page stacks settled / resuming / since-you-left / not-yet-disclosed sections the reader must parse before reaching any numbers, working against the "calm, dense, factual, ten-minute scan" job that A's flat table serves more directly.

## Why variant-c over variant-b

1. C states a verdict, a score and at least one kill-criterion on every row before any click; B's queue rail — the actual list of pending decisions — shows only venture name, id and ₹ amount for most queued items (Saathi Health, Vahaan Logistics, Bazaarly), with verdict and kill-criteria state revealed only once a row is opened into the detail pane. That is a more direct break of "visible before that action ... on the card, never behind a click," since the object the brief names (the approval card) doesn't carry its own required facts in B's list view.
2. C keeps a real, substantial "today" record — ten dated one-line events running through to a "later today, not yet disclosed" section — that functions as the brief's event timeline. B's equivalent, "TODAY'S EVENTS," is three short lines tucked under the queue rail, visually minor next to the KPI row — a much thinner answer to "always visible: ... today's event timeline" as a co-equal surface.
3. B's queue rail shows two rows carrying the identical blue selection border at once (Kirana Express at top, Bazaarly at bottom) — for a keyboard-first, single-selection model this reads as a real selection ambiguity in the exact surface the expert path (j/k) depends on.
4. B's own shortcut legend prints "k" for two different actions in the same line ("j k rail ... k kill") — a visible conflict in the one place the brief's "faster once learned" expert path lives. C and A each keep one unambiguous letter per action.
5. In B's favour, and why this is close rather than a rout: B is the only variant to label a section "COUNCIL VERDICT" verbatim (the closest match anywhere in the run to the brief's own spine noun), and the only one to show reject-reason presets as real, visible pill buttons ("Evidence insufficient," "Runway below floor," ...) rather than a promised prompt — a genuine, checkable answer to "r rejects with a reason prompt" that neither A nor C actually renders on screen.

## What would change my mind

B's per-item depth is real and the strongest thing any variant does: its kill-criteria panel breaks one venture into four named, floor-vs-actual metrics (runway, burn, gross margin, MRR growth) each flagged OK / near-breach / breached, and its always-visible reason-preset row is the only place in the run where "reason required" is an actual clickable set of controlled terms instead of a promise in a header. If A or C paired that same per-decision criteria depth with their own at-a-glance, all-cards-visible layout, that variant would win outright.
